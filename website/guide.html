Documentation / FNK0104S

From first build
to first image.

A practical path through installation, file transfers, and optional display integration.

Reference environment: ESPHome 2026.8.0, ESP-IDF 5.5.5, Freenove FNK0104S / ESP32-S3R8, 8 MB octal PSRAM at 80 MHz, and a prepared FAT32 card on four-bit SDMMC. These versions describe the documented setup; compatibility with newer releases is not guaranteed.

01 / Installation

Begin with the complete example.

  1. Download the repository

    Download the master ZIP and extract it on the machine running ESPHome. Keep examples/fnk0104s-esp-idf.yaml, examples/assets/, and components/ in their original layout. The checkout must be accessible inside your ESPHome container if you use one.

  2. Prepare secrets and the SD card

    Copy secrets.example.yaml to examples/secrets.yaml. Replace the Wi-Fi placeholders and generate a random key locally, for example with openssl rand -hex 32. The API key must contain at least 32 UTF-8 bytes. Keep the file private and ignored by Git. Use a prepared FAT32 card and retain format_if_mount_failed: false.

    examples/secrets.yaml · template only
    wifi_ssid: "YOUR_WIFI_SSID"
wifi_password: "YOUR_WIFI_PASSWORD"
sd_server_api_key: "REPLACE_WITH_YOUR_RANDOM_KEY"

  3. Validate, compile, and flash

    With ESPHome 2026.8.0 installed, run from the repository root. Replace the serial port with your board’s port. Compilation does not need the actual JPEG/BIN files on the SD card; the local placeholder SVG must be available on the build machine.

    Shell · repository root
    esphome config examples/fnk0104s-esp-idf.yaml
esphome compile examples/fnk0104s-esp-idf.yaml
esphome upload examples/fnk0104s-esp-idf.yaml --device /dev/ttyACM0

    Subsequent firmware updates use normal ESPHome OTA or the dashboard. The SD file upload endpoint does not flash firmware.

  4. Open the device and provision images

    After boot, open http://fnk0104s-sd-server.local:8080/sd/ in your browser, or substitute the device IP address. Enter your API key, create the required folders, and upload files to the exact paths in display_images.images.

    Missing initial images leave placeholders in the widgets while the file server still starts. Restart after provisioning to load every initial image, including static widgets. A widget with a Select can also load a newly uploaded image by selecting it. Upload alone does not assign it.

Keep the wiring and memory settings.

The full example configures the display and backlight as well as a 16 KiB loop-task stack for JPEG decoding. The same board name does not imply identical wiring on another “CYD” device.

03 / SD images

Map names. Bind widgets.

Add the following display_images block inside the existing cyd_sd_http_server: section of the full example. This reduced mapping uses the example’s sd_display_image widget; remove its other image mappings/widgets or retain them in your configuration.

YAML · optional component fragment
  display_images:
    drive_letter: S
    cache:
      max_size: 1MB
      file_buffer_size: 16kB
      memory: psram
      strategy: lru
    images:
      - name: Image 1
        path: /Image1.jpg
      - name: Image 2
        path: /images/Image2.jpg
    widgets:
      - image_widget: sd_display_image
        initial_image: Image 1
        fit: contain
        select:
          id: sd_display_image_select
          name: Display image

Each image_widget must refer to an existing, uniquely bound LVGL image widget. The full example supplies a 1 × 1 compiled SVG placeholder as its initial src. The component replaces that source during setup; no boot lambda is required. The legacy singular display_image configuration remains supported.

Direct SD rendering formats
FormatSupport
.jpg / .jpegBaseline JPEG through LVGL’s Tiny JPEG decoder
.binLVGL 9.5-compatible binary image assets; not arbitrary BIN files
PNG / progressive JPEGUnsupported by the direct SD image path. Convert on your computer first.

What needs another build?

Image names, paths, widget bindings, and Select options are compiled into firmware. Adding or changing them requires rebuilding and flashing. Replacing the file contents at an existing mapped path requires no rebuild; reselect the image or restart to load it. There is no runtime directory scan or HA image-list refresh button yet.

Optional host-side conversion

The LVGL BIN converter handles PNG/JPEG input, resizing, rotation, and transparent-background compositing on your computer. It requires Pillow, installed from add_tools/requirements.txt. This optional firmware asset tool is separate from the dependency-free website.

04 / Home Assistant

Control each image independently.

With the normal ESPHome api: connection, each widget can expose its own image control. Every control shares the compiled image list; changing one widget does not change the others.

Per-widget control modes
ConfigurationHome Assistant interface
Omit select:Static startup image; no image entity
select:Image dropdown (select.*)
select: with hidden: trueRead-only text status (sensor.*) plus an image-selection action

Hidden Select for automations

Inside a widget’s existing select: block, add hidden: true. The component generates the status sensor and native API action automatically. The original Select ID remains usable for local ESPHome automations. This is a presentation choice, not an access restriction.

YAML · replace this widget’s select block
        select:
          id: sd_display_image_select
          name: Display image
          hidden: true

For the standard example, call the following action from HA. option must exactly match an allow-listed image name. HA prefixes the generated cyd_sd_set_<image_widget_id> action with the device name.

Home Assistant · action fragment
action: esphome.fnk0104s_sd_server_cyd_sd_set_sd_display_image
data:
  option: Image 2

Unknown names and detected file-access failures keep the previous source and status. The status confirms source assignment, not completion of a later streaming decode. The action has no result response; inspect status and logs. Reboot reloads initial_image; use an HA availability trigger if an automation should restore a selection.

Changing between visible and hidden mode requires rebuilding and flashing, changes the HA entity domain, and requires migrating existing automations and possibly removing stale HA entities. See the mixed-mode example.

Native PSRAM diagnostics

Enabling image support automatically creates six byte-valued diagnostic sensors: PSRAM total, free, and largest free block; cache limit, used, and reclaimable. A Release Unused SD Image Cache button frees only frames assigned to no widget. Assigned images remain visible, including on hidden pages.

Values are checked every 10 seconds and after selections and releases; unchanged values are not republished. HA can plot recorded sensor history. The device-wide free PSRAM value includes other components; cache-used counts decoded RGB565 pixel buffers only.

05 / Cache & scaling

Budget memory deliberately.

The decoded cache defaults to max_size: 1MB, configurable from 0 to 4 MB. It allocates RGB565 buffers only in PSRAM, on demand. The budget is not preallocated and cannot guarantee that a sufficiently large contiguous block exists.

Entries are shared by SD path. LRU eviction protects every frame still assigned to a widget. A 320 × 480 image uses 307,200 decoded bytes; three fit in the default budget. Scaling a source into several widgets does not add a second decoded source buffer or reduce its memory cost.

Per-widget fit modes
ModeBehavior
Omitted / noneUnscaled placement; smaller widgets can crop the source
containPreserve aspect ratio; show the full image, centered
coverPreserve aspect ratio; fill the widget and possibly crop edges
stretchFill both dimensions; aspect ratio may change

Fitted widgets require a successful decoded cache entry. If allocation or decoding fails, they keep their previous image and Select state. Unscaled widgets can fall back to direct S:/ streaming. Set max_size: 0 to disable decoded caching and omit fit when using that path.

The separate file_buffer_size: 16kB cache belongs to each open LVGL file and combines small reads. Setting it to 0 disables file-read caching. Cache hits avoid reading and decoding the image body, but still probe file availability and perform normal LVGL drawing. Uploading or deleting a mapped file invalidates its decoded generation; reselect to load changed content.

Adding fit enables LVGL RGB565A8 software transform support at compile time and requires a rebuild and flash. The maintainer confirmed contain scaling and shared-buffer behavior; detailed cover, stretch, eviction, and failure cases remain open in the hardware matrix.

06 / HTTP API

A small API for your own tools.

Every /sd/api/* request requires X-API-Key. Use virtual paths relative to the SD root, such as /photos/photo.jpg, and URL-encode query values. Do not send internal /sdcard/… or LVGL S:/… paths.

@@API_ROWS@@
Implemented endpoints
MethodEndpointPurpose

Authenticate and check health

These examples use Bash. Read the key without putting its literal value into shell history.

Bash · device on your trusted LAN
SD_BASE_URL='http://fnk0104s-sd-server.local:8080'
read -r -s -p 'SD API key: ' SD_API_KEY
export SD_API_KEY
curl --fail-with-body --show-error \
  -H "X-API-Key: $SD_API_KEY" "$SD_BASE_URL/sd/api/health"

Create a folder and upload a raw file

Create parents first; skip folder creation if it already exists. Uploads require an explicit Content-Length and application/octet-stream. Use a regular input file so curl supplies the length. Multipart and chunked uploads are unsupported.

Bash · creates /photos and uploads photo.jpg
curl --fail-with-body --show-error -X POST \
  -H "X-API-Key: $SD_API_KEY" \
  "$SD_BASE_URL/sd/api/directory?path=%2Fphotos"

curl --fail-with-body --show-error \
  -H "X-API-Key: $SD_API_KEY" \
  -H "Content-Type: application/octet-stream" \
  --data-binary @./photo.jpg \
  "$SD_BASE_URL/sd/api/file?path=%2Fphotos%2Fphoto.jpg&overwrite=false"

Stream and verify with Python

The repository’s uploader uses the Python standard library. It reads SD_API_KEY or prompts without echo. --verify downloads to a temporary local file and compares SHA-256; it keeps the remote upload. Add --overwrite only for an intended replacement.

Shell · repository root, after creating /photos
python3 scripts/upload_file.py \
  http://fnk0104s-sd-server.local:8080 ./photo.jpg /photos/photo.jpg --verify

The device streams uploads and downloads in 8 KiB blocks; it does not buffer entire transfers in RAM or PSRAM. Browser downloads currently build a Blob on the client, so browser memory use is separate. One upload is allowed at a time. The API lists up to 100 entries per page with offset and limit; the current WebUI shows the first 100 and directs you to the API for further pages.

Errors use a JSON envelope with operation, path, and machine-readable error details. Downloads instead return the file body and exact Content-Length. Common statuses include 401 for authentication, 409 for conflicts, 411 for missing length, 413 for excessive size, 503 for unavailable storage, and 507 for insufficient space.

07 / Security & limits

Keep it on a trusted network.

HTTP sends the API key and file data in clear text. Use a trusted, segmented LAN, firewall port 8080, and never expose the device to the public internet. There is no TLS, per-user authorization, or brute-force throttling. The website you are reading is static documentation; device credentials belong only in the device WebUI or your local tools.

The component implements centralized path validation, a constant-work API-key comparison, synchronized storage with active-reader protection, free-space checks, a configurable upload limit, temporary-file staging, checked writes and finalization, and recoverable overwrite backups. The embedded same-origin UI uses no CDN and holds its API key in sessionStorage.

These safeguards are implemented, but FATFS is not transactional. Boot recovery attempts to restore interrupted overwrite backups and remove stale uploads; it cannot guarantee integrity during power loss, corruption, or physical card failure. Keep independent backups. Systematic failure, concurrency, and endurance testing remain pending.

  • No recursive directory creation or deletion; delete only empty folders.
  • No hotplug; power down before removing the card.
  • No Arduino framework, other boards, or SPI SD support.
  • No PNG/progressive JPEG decoding in the direct image path.
  • Directory timestamps are best effort without configured time synchronization.
  • Directory/wildcard image discovery and MP3 playback are plans only.

08 / Troubleshooting

Check the path, then the logs.

The image is still a placeholder

Verify the SD mount, exact allow-listed name/path, and baseline JPEG or compatible BIN format. Create parent folders before upload. Uploading an image does not automatically assign it: reselect it or restart. Static widgets load their initial image at startup.

A fitted image will not change

Check PSRAM free space, its largest free block, and the cache budget. Fitted widgets require the full decoded frame. They deliberately keep the previous image if caching fails. Keep loop_task_stack_size: 16384 and rebuild after enabling fit.

An upload or delete returns 409

An upload is already active, the target exists without overwrite permission, or an active reader conflicts with the operation. Wait for the operation to finish and opt into overwriting only when intended.

Uncached image selection takes noticeable time

The first load reads and decodes from SD. The maintainer observed occasional computation warnings of roughly 150–850 ms. Cache hits avoid decoding the body but still redraw through LVGL and the display bus. No universal latency or throughput guarantee is claimed.

The SD card does not mount

Check FAT32 preparation, documented GPIO wiring, suitable pull-ups, and the power supply. Keep format_if_mount_failed: false; formatting is not a safe diagnostic step for a card containing data.
